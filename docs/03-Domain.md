# Domain and ubiquitous language

**Project:** focus-kit
**Status:** active
**Last updated:** 2026-09-18

---

## Purpose

This document defines the entities of focus-kit, their invariants and the
**ubiquitous language** of the project.

It is the pivot document: every delivery in `work/`, every identifier in
code and every test uses the terms defined here. Each concept has exactly
one meaning, and the same concept never receives two names.

focus-kit is unusual in one way worth stating here: most of its domain is
made of files and paths rather than records in a database. A term's code
name is therefore often a path, a bash function, or a marker string. That
does not make it less normative. A delivery that invents a second name for
`work/done/` has broken the same rule as one that invents a second name for
an aggregate.

## Term in code

Concepts are defined in prose; every identifier in code, schema and API is
written in English, whatever language this document is in. So that the
translation from concept to identifier is made once and not renegotiated
file by file, each term declares its canonical code name. The table is
normative: no delivery may name in code a concept that is not here.

The listed form uses `camelCase` where a symbol is meant. The concrete
casing follows the artifact: `snake_case` for bash functions, lowercase
hyphenated for slugs and file names, uppercase for `VERSION`.

**A new concept enters here first**, with its code term, and only then
appears in a delivery.

### The kit and its parts

| Term | Code | Short meaning |
|---|---|---|
| Kit | `focus-kit` | This repository, and the thing it installs. Both senses are the same artifact: the repository is the kit's source, the installed files are the kit in a target. |
| CLI | `bin/focus-kit` | The single executable. Five verbs: `install`, `update`, `doctor`, `version`, `selftest`. |
| Uninstall | `focus-kit uninstall [path]` | The verb that takes the kit back out of a target: every Kit-owned file the Manifest lists plus the stamp and the manifest themselves, what the Settings baseline merged into `.claude/settings.json`, the two Leftover entries an earlier kit merged, and the block each Appended once file received, down to its End marker. It touches no Project-owned file and no dependency on the machine. It reports rather than asking, and carries no flag and no prompt, because what it removes `focus-kit install .` puts back, with git or without it. Two things it takes do not come back, and the run says which: a Kit-owned file the person edited, which returns as the kit's version and not theirs, and that one is a `warn`; and a Leftover, which returns not at all, and that one is the `ok` line of the file it left, because there is nothing for the person to do next and the entry going is the point. It is the one place the CLI removes a key from a Merged file, which `ADR-0002` forbade until this delivery amended it. Added by `uninstall-removes-the-kit`. |
| Kit version | `VERSION` | One line, semantic version. Read at startup into `KIT_VERSION` (`bin/focus-kit:54`). |
| Upstream version | (three lines of `doctor` and of `install`) | The `VERSION` at the default branch of the clone's own `origin`, compared with `KIT_VERSION` by `doctor` and by the dependencies block of `install` and `update`. It is the half of staleness the kit reported about nothing: the Installed version says whether a target matches the clone, and this says whether the clone matches what it was cloned from, which is the number `focus-kit update` would otherwise carry into every target for months. Read over HTTPS, read-only on the clone and bounded: no ref, no object and no file is written, and an `origin` that does not answer becomes a line and never a wait. The remote is derived from `origin` and never written into the script, so a fork checks the fork. Three states, one wording held in one function with two callers: `kit source <v>, origin has <v> (git -C <clone> pull, then focus-kit update)`, the green `kit source <v> (nothing newer on origin)`, which says nothing newer rather than equal because a clone ahead of `origin` is the normal state between a commit and a push, and `kit source <v>, origin did not answer (check by hand: git -C <clone> pull)`, which covers a machine with no network, an `origin` the derivation does not cover, a reader absent from PATH and an answer that does not read as a version, since a page taken for a number is a warn that lies. The ordering of the two numbers is `version_lower()` (`bin/focus-kit:104`) since this delivery, with two callers, the second occurrence of a shape `global_skill_state` held alone until now. Neither Drift, nor a Leftover, nor an Unbumped change: those three are about a target, and this one is about the clone all three are measured against. The number is the `VERSION` file and never a tag or a release, since the kit has no release artifact and no tag flow (The kit, Transitions). Added by `update-alert`. |
| Installed version | `.claude/skills/.focus-kit-version`, read by `installed_version()` | The kit version stamped into a target at install time. Written with LF; read with every carriage return removed, so a target cloned on Windows with `core.autocrlf=true` compares equal instead of reading `0.5.2` as not `0.5.2`. Nothing else is trimmed: a leading or trailing space is still a difference. The read goes through `without_cr()`, the one place a carriage return is forgiven. `doctor` compares it with `VERSION` to say whether the target is stale, and where the two are equal it asks the second question the number alone cannot answer, the Unbumped change below: the green `kit version <v>` line is printed only when the number and every kit-owned file agree with the source. In this repository it equals `VERSION` at every commit (check 6 of `selftest`). |
| Manifest | `.claude/skills/.focus-kit-manifest`, written by `write_manifest()` | What `install` wrote into a target: one line per kit-owned file, its fingerprint and its path relative to the target, sorted with `LC_ALL=C sort`, LF. Read by `doctor` to tell an edited file from a stale one, which comparing the target with the kit source cannot do once the kit has moved on. Kit-owned: rewritten on every install, never edited by hand. A target installed before it existed has none, and `doctor` says so. |
| Fingerprint | `fingerprint()` | The POSIX `cksum` CRC of a file's content read through `without_cr()`, so a Windows checkout with `core.autocrlf=true` fingerprints the same as the install that wrote the manifest. `cksum` because it is specified by POSIX and present on macOS, Linux and Git Bash without a probe. Written by `write_manifest`, compared by `doctor`. |
| Command | `skills/<name>/SKILL.md` | One of the four things a person types in Claude Code: `/initialize`, `/discuss`, `/propose`, `/apply`. Called a skill by Claude Code and a command by this project; the two words mean the same thing here. The number is not written into `bin/focus-kit`: every place there that enumerates the commands reads the `skills/` tree through `kit_skills()`, the way it reads `manuals/*.md`, so a fifth one is a folder and no edit (`discuss-adds-queue-line`). |
| Host | `kit_hosts()`; `docs/01-Architecture.md` §4 | The agent tool that reads a target's Commands. Two of them since `copilot-port`: Claude Code, which reads `.claude/skills/<name>/SKILL.md`, and GitHub Copilot, which reads a Ported command. One Command, one text, one file per host, because the second file is generated from the first and never written beside it (`ADR-0007`). No Command's text names a host, and since `graph-builds-without-a-key` no Manual does either: what is host-specific is the substitution list of the transform and the list `kit_hosts()` holds, both in `bin/focus-kit` and nowhere else. That function is where a Host's three facts live, the platform name graphify's own installer takes, the directory that installer places its Global skill in, and the name a person reads, so a third Host is a line there plus its substitution entries. |
| Host instructions | (one file per Host; `CLAUDE.md` for Claude Code) | The file a Host reads at the start of every session in a target, before any Command. `CLAUDE.md` is the one Claude Code reads and the one `/initialize` fills from a Template; every other Host gets a short file that points at it rather than a second copy of it, written in every target and without asking, so one edit by hand moves every host and nothing drifts. Project-owned, all of them: a person may add a line, and `update` erases a Kit-owned file. Added by `copilot-reads-the-project-rules`. |
| Ported command | `render_prompt()`, one file per Command per Host other than Claude Code | The Host's copy of a Command, generated at install from `skills/<name>/SKILL.md` and never authored beside it (`ADR-0007`): the same body word for word, with a fixed substitution list replacing what names Claude Code alone. Five pairs, in `render_prompt` and nowhere else: the argument placeholder, the tool that asks, the new session, the proof tool option that is a browser inside the host, and the host itself. **What every target has whatever its host is not in the list**, which is why `CLAUDE.md` is not, the Host instructions file pointing at it rather than replacing it, and why `.claude/skills/initialize/templates/` is not, the install writing it at that path in every target. The frontmatter is carried over as it is, its keys being three the host's own format names, plus the one line that puts the host in the mode a command writing files needs. Kit-owned, listed in the Manifest, carrying the Kit-owned banner and the License notice, so the next `update` overwrites an edit made in a target; **the directory that holds them is not**, being where a person keeps their own prompts, so `install` writes its own files into it and removes nothing, the way `docs/manuals/` works. Of Drift it therefore reaches two shapes and not the third: edited locally and missing, never `is not the kit's`, which would name a removal that does not happen. Its directory, its name, its extension and its frontmatter keys are the host's to declare and the run's to read, never this table's to pin. Added by `copilot-port`. |
| Manual | `manuals/<name>.md` | A kit-owned how-to document: `process.md`, `focus.md`, `graphify.md`. Copied to `docs/manuals/` of every target. |
| Translated manual | (a Manual in a target's Documentation language, recorded by the Manual language below) | A Manual after `/initialize` wrote it in the target's Documentation language: the body in that language, every section heading still in English, because a Command names the section it reads and `doctor` matches a Manual citation against the manual at `KIT_DIR`, so a translated heading would break both. All three, `focus.md` included, and what that costs is the reason `docs/00` (Audience) gives for quoting the book verbatim. Kit-owned like the Manual it comes from, so `install` and `update` go on writing English over it and what translates it again is `/initialize`, a command the person ran: no fifth ownership category and `ADR-0002` untouched. The target records which language its manuals are meant to be in, in the Manual language file `/initialize` writes and the CLI only reads; the Manifest goes on holding the English fingerprint `install` wrote, so `write_manifest`, `install` and `update` are untouched and the Unbumped change pass keeps agreeing with the kit source, while Drift is the pass that gains the exception and skips the three manuals where the record is not English. `doctor` says in one line when they are English again and names `/initialize`. Added by `manuals-follow-the-language`, which is what closes open decision 4 of `docs/00` and what makes Language of the interface below stop saying the kit's own strings are never translated. |
| Manual language | `.claude/skills/.focus-kit-language`, written by `/initialize` and read by `doctor` | Which language a target's Manuals are meant to be in: one line ending in a newline, LF, an IETF BCP 47 tag, which is an Identifier and so stays English whatever the Documentation language is. `en` for English, and **absent means `en`**, which is every target installed before it existed and what keeps the delivery that adds it from changing any of them. Its path sits beside the Installed version and the Manifest, the two other files under `.claude/skills/` that are data and not a Command, which `copy_tree` never wipes because it overwrites `.claude/skills/<name>/` and not their parent. Read through `without_cr()` like the stamp, since a target versions it and receives no `.gitattributes`. Project-owned, and the one file of that category no person is expected to type: `/initialize` writes it at the step where it asks the Documentation language, on a first run and on a review run alike and including when the answer is English, the CLI only reads it, and that is what keeps the four ownership categories at four. `doctor` compares it with `en` and, where the two differ, asks of each Manual whether it is still the English file the kit ships. Not the Documentation language itself, which is declared in prose in three places for a person to read: this is the machine-readable half, held once so that no part of the CLI parses a sentence. Added by `manuals-follow-the-language`. |
| Named section | `§<heading>`, in a command's text | The part of a manual a command reads: from the heading the command names to the next heading of the same level, and nothing else of the manual. A command that names a section reads that section alone; the section stays written in the manual, in one place, and the heading is what the command hangs on, so renaming a heading is a change to every skill that names it. What a command does not name of a manual it does not read. First occurrence: `commands-read-sections-not-manuals`, measured over 194 sessions, where the three commands read `graphify.md` whole for §Ensuring the graph and every `/apply` read `focus.md` whole for two of its sections. |
| Template | `skills/initialize/templates/` | The skeleton of a document `/initialize` fills. Mirrors the target layout: `CLAUDE.md` and `docs/`. |
| Init comment | `<!-- init: ... -->` | Guidance written to `/initialize` inside a template. It says what goes in the section. `/initialize` fills the section and removes the comment; none may survive into a finished document. |
| Settings baseline | `config/settings.baseline.json` | The permissions merged into a target's `.claude/settings.json`: what `allow`, what `ask`, what `deny`. The only baseline the kit has, since `mcp-leaves-the-baseline` deleted the MCP one. Never replaces what is there. |
| Gitignore fragment | `config/gitignore.fragment` | The block appended once to a target's `.gitignore`, guarded by the marker `# --- focus-kit ---`. |
| End marker | `# --- focus-kit end ---`, the last line of each fragment | Where the block an Appended once file received stops. The first line has always said where it starts, and `append_once` guards on that one; with no second the block has no end, which is why nothing can tell a line an older fragment dropped from one the person wrote, and why the block could not be taken back. Same style and same block as the first marker, not a second one (`ADR-0002`, amended). It begins with `#`, so it is not a pattern line and no target gains a Fragment gap warn for it. A target that installed before it existed has a block without it, and `append_once` leaves an existing block alone, so it never arrives there: `Uninstall` leaves that file where it is and names the block for a hand removal, because nothing else says where it ends. Added by `uninstall-removes-the-kit`. |
| License | `LICENSE` | The terms the kit is published under: GNU AGPL-3.0-only, verbatim so GitHub detects it. Lives only in this repository; the CLI never copies it. Terms outside it are granted only by the author (`docs/adr/ADR-0004`). |
| License notice | (one HTML comment line) | The single line naming the copyright holder, the license and the source repository. Carried by every kit-owned file a target receives and by the CLI's header, so a copy names its author wherever it is seen. |
| Kit-owned banner | (one HTML comment line) | The line on a Kit-owned document saying the file is the kit's and that the next `update` overwrites an edit made in a target. One wording for the rule, held in `manuals/process.md` line 1 and taken from there rather than retyped. The three manuals carry it on their first line; since `skill-says-it-is-kit-owned` the four `SKILL.md` files carry it on the first line after the frontmatter's closing `---`, because a comment above line 1 is not valid YAML and check 4 dies when line 1 is not `---`. It sits ahead of the License notice, the order the manuals have. ADR-0002 forbids a Kit-owned file without it and excepts the two data files `doctor` reads; the ten Templates carry none, and the ADR's amendment records that gap rather than closing it. |

### Ownership

| Term | Code | Short meaning |
|---|---|---|
| Kit-owned | `copy_tree()` | A file the CLI overwrites on every `install` or `update`: the skill folders, the three manuals, the Ported commands, the installed version and the manifest. Editing one inside a target is a change that the next update erases, and `doctor` reports it as drift. It is edited in this repository, except for a Ported command, which is generated from the skill it comes from and edited nowhere (`ADR-0007`). The two data files carry no Kit-owned banner, because `doctor` reads them. A file being kit-owned says nothing about the directory holding it: `docs/manuals/` and `.github/prompts/` are the target's, and what `install` overwrites there is its own files, one by one. |
| Drift | (three `warn` lines of `doctor`) | A kit-owned file in a target that is not as `install` wrote it: a file in the manifest whose fingerprint changed, a file in the manifest that is absent, or a file added inside one of the skill folders. Each is lost or already gone on the next `update`, and `doctor` says which: `<path> edited locally (focus-kit update overwrites it)`, `<path> missing (focus-kit update restores it)` and `<path> is not the kit's (focus-kit update removes it)`. An absent file loses nothing, because `update` restores it, and it is still drift: the manifest is the only complete list of kit-owned files a target holds, so silence about one is a green line that was not earned. Three shapes and no fourth: the kit-owned paths the presence lines of `doctor` name, the skills and the three manuals, print the absent shape word for word, which is why the drift pass can stay silent about a path they named without the reader seeing two wordings for one state. A stale target is not drift: the kit moved, the file did not. One exception, and it is the Manual language's: where a target's Manuals are meant to be in another language, the three `docs/manuals/*.md` entries are not fingerprinted, because the Manifest holds the English file `install` wrote and the disk holds the Translated manual, so the pass would call all three edited locally and the one thing it would name is the delivery working. What is asked of them instead is whether a translation happened at all, which is the line the Translated manual row above describes. The absent shape is not excepted, since a manual a target does not have is missing whatever language it was meant to be in. Added by `manuals-follow-the-language`. |
| Unbumped change | (one `warn` line of `doctor`) | A kit-owned file in a target that is as `install` wrote it and not as the kit source at `KIT_DIR` holds it now, while the Installed version equals `VERSION`: the kit moved and the number did not. Neither Drift, because the file did not move, nor a stale target, because the number agrees; the manifest and the version compare answer each other and neither asks the source. `doctor` asks it in every target, since the CLI runs from its clone and `KIT_DIR` is always there, and only when the number is equal and the manifest exists: `<path> behind the kit source (run focus-kit update)`, one line per file, the target's path, for a source counterpart that differs from the manifest's fingerprint, one that is gone, or a source file the manifest never listed. While any prints, the green `kit version <v>` line does not, so that green means number and content both. First occurrence: the first target on 2026-09-17, updated mid-delivery and reported green after the source moved (`doctor-sees-an-unbumped-change`). |
| Project-owned | (never written by the CLI) | A file only `/initialize` and the people working in the target may touch: `docs/00` to `06`, `CLAUDE.md`, `docs/adr/`, `work/` and the Manual language. The CLI never writes one. It reads three of them: `install_repo` checks whether `docs/00-Product.md` exists, to decide which next step to print (`bin/focus-kit:551`), `doctor`'s Manual citation pass reads `CLAUDE.md`, `docs/00` to `06` and everything under `docs/adr/` line by line, `work/` excepted, and `doctor` reads the Manual language to know which language the Manuals are meant to be in. Reading is not what `ADR-0002` forbids, which is the write. The Manual language is the one file of the category no person is expected to type and the one that does not live under `docs/` or `work/`: what makes it project-owned is who writes it, `/initialize` and never `install` or `update`, and not where it sits. |
| Merged | `merge_json()` | A file the CLI adds to and never removes from: `.claude/settings.json`, and since `mcp-leaves-the-baseline` no other. One rule decides every key a baseline holds: an absent key is taken, two objects merge recursively, two lists concatenate without duplicates, anything else is the baseline's, and a key the baseline says nothing about is untouched. Four cases and no carve-out: the `mcpServers` one left with the baseline that needed it. The merge goes through python3 and is idempotent. `doctor` reads the file back and says whether what the baseline put there is still in it, asking for `"Bash(graphify *)"`. Presence earns no green line, because a file that reads `{}` exists and leaves every permission unasked for, and what the warn names is `focus-kit update`, which merges the baseline back. |
| Leftover | (two `warn` lines of `doctor`) | An entry an earlier version of the kit merged into a target and the current version no longer ships. Merged is additive, so `update` leaves it where it is, and `doctor` names it together with the hand removal that ends it: `.mcp.json still declares the graphify server (...)` and `.claude/settings.json still enables the graphify server (...)`, each pointing at `docs/manuals/graphify.md` §Troubleshooting. The first occurrence is the graphify server that `mcp-leaves-the-baseline` stopped shipping; a second one earns the `uninstall` mechanism the Later list holds, not a third wording. A Leftover is not Drift: the file is the target's, and the person decides when the entry goes, not `update`. |
| Appended once | `append_once()` | A file the CLI adds a fragment to the first time and never again, because the marker line is already there. Two files: `.gitignore` (the first occurrence, `config/gitignore.fragment`) and `.graphifyignore` (`config/graphifyignore.fragment`, which keeps the kit's own skills and manuals out of the graph). Both are the target's own files, versioned by the target, and what `install` writes is the whole block or nothing: a block that is there is never touched, so no line the person removed comes back. What `doctor` reports of them is therefore not the file but what it lacks of the fragment the kit ships now, which is the Fragment gap below. |
| Fragment gap | (two `warn` lines of `doctor`) | What a target's Appended once file lacks of the fragment the kit ships now: a pattern line, one that is neither blank nor beginning with `#`, that no whole line of the target's file equals once carriage returns are removed, or the marker absent altogether, which is the file a target installed before that fragment existed never received. Two shapes, because the two states have two fixes: `<file> lacks the kit's line "<the line>" (add it by hand; focus-kit update leaves an existing block alone)`, one warn per line, and `<file> has no focus-kit block (run focus-kit update)`. A whole line and never a substring, because an old target holds `graphify-out/cost.json` and lacks `graphify-out/`, and a substring test would go green on exactly the case the term exists for. The green line is `<file> (kit fragment current)`, printed when every pattern line is there. Not Drift: the file is the target's own, `update` never touches a block that is there, and nothing is lost. Not a Leftover: the kit still ships the line, and the target never received it rather than keeping something the kit dropped. What it cannot see is a line an older fragment had and this one dropped, because with no end marker nothing tells that line from one the person wrote. First occurrence: `graph-rebuilds-on-demand` (`70945b8`), which rewrote the `.gitignore` block to `graphify-out/`; second: `discuss-adds-queue-line` (`9f09c7e`), which added `.claude/skills/discuss/` to the `.graphifyignore` one. Added by `an-old-target-gets-the-fragment`. |
| Manual citation | (two `warn` lines of `doctor`) | A reference from one of a target's repeatedly read documents, `CLAUDE.md`, `docs/00` to `06` and `docs/adr/`, to a section of a kit-owned Manual: the text `manuals/<name>.md` followed by a `§` with nothing between the two but backticks and spaces, and then whatever runs to the end of the line. `manuals/` is part of the key, because a target's own `docs/05-Process.md` is one file name away from `process.md`. A citation is stable only when it names the heading, since `update` may overwrite the manual with one whose sections moved and the citation sits in a file the CLI may not edit. Two shapes, because two things go wrong. A citation **by number**, what follows the `§` beginning with a digit, is named on sight: a section inserted in a manual renumbers every one below it, and the number goes on pointing at a section that now means something else. A citation **by heading** is named when no normalized heading of that manual is a prefix of the text after the `§`. A heading is normalized by removing its `N. ` numbering and cutting it at the first comma or opening parenthesis, so `## 5. Errors are values (ch. 8)` gives `Errors are values`, which is what lets a citation carry the heading in the words its sentence needs. A prefix and never a whole line, because a citation ends inside that sentence and nothing marks where: `§Ensuring the graph` is followed by a comma in one document, a full stop in another and a table pipe in this one. The comparison is against the manual the kit ships at `KIT_DIR` and never against the target's copy, because what is at stake is what the next `update` writes. The two lines are `<path>:<line> cites docs/manuals/<name>.md by number: "§<the rest of the line>" (cite the heading by hand; a section added to that manual renumbers the ones below it)` and `<path>:<line> cites a section docs/manuals/<name>.md does not have: "§<the rest of the line>" (fix the citation by hand; the heading moved or was renamed)`, one per citation; the green line is `project-owned documents (every manual citation by heading, every heading there)`, printed when neither warn did, a target `/initialize` never ran in included. Both fixes are a hand edit, because ADR-0002 forbids the CLI an edit to a Project-owned file and what the citation meant is only in the sentence around it. `work/` is not read, in flight or done: a Delivery is read by the one session that builds it, and a Done page records what was, which a correction would falsify. Because the heading runs to the end of the line, a citation the line wrap cuts between the `§` and the end of the heading gets the second warn, and one whose file name and `§` fall on either side of the wrap is not seen at all: a citation is written on one line or it is not written. Two of this repository's own documents were wrapped that way and were rewrapped when the pass named them. Not Drift: the file is the target's own. Not a Leftover: the kit still ships the manual. Not a Fragment gap: nothing is missing from a file the kit appends to. A citation inside a kit-owned file is not read at all, because `update` replaces the citing file and the cited manual in one run. A sentence explaining the defect keeps the number away from the file name, the way the next one does, so the prose does not report itself. First occurrence: `docs/adr/ADR-0006-focus-is-asked-not-imposed.md` in this repository, which names the house rules as §6 of `manuals/process.md`, moved to §7 when `discuss-adds-queue-line` (`9f09c7e`) inserted `## 4.`. Added by `update-survives-a-moved-section`, which closes open decision 5 of `docs/00-Product.md` in `ADR-0002`. |
| Target repository | `target` | The repository the kit is installed into. Inside the CLI it is always an absolute path (`bin/focus-kit:490`). |
| Dogfood copy | `.claude/skills/`, `docs/manuals/`, `.github/prompts/` | This repository is also a target of itself. The first two paths hold copies of `skills/` and `manuals/`; the third holds the Ported commands, which are not copies of anything and are compared against a regeneration instead of a `diff -r`. All three are versioned, and keeping them equal to their sources is a rule, not a habit (`docs/05-Process.md` §5). |
| First target | `~/Downloads/vaulted` | The one target repository that is not this one and that milestone 2 runs the whole cycle on: a clone of someone else's public repository, installed by `first-target-install`, initialized by `first-target-initialize`, taken through one delivery by `first-target-delivery`. Every friction it produces comes back to the queue as a line. Nothing is committed or pushed there, ever: it is a clone, not a repository this project owns. What a command stages there (`/initialize` and `/apply` both end with `git add -A`) is undone with `git reset` before the record is written, so the clone is never one keystroke from a commit; the working tree stays as the last run left it, because the clone is disposable and nobody needs it back at its first commit. It is a row of `docs/05-Process.md` §5 while milestone 2 is open and leaves with it. |

### The delivery process

| Term | Code | Short meaning |
|---|---|---|
| Delivery | `work/<slug>.md` | One unit of work, defined on one page. The page is the scope. |
| Contract | `**Contract.**`, a section of `work/<slug>.md` | The one section of a Delivery that must be exact (`docs/05-Process.md` §3), and exact means what must hold, not what only a run settles. Of a tool or dependency it holds what a document can hold: the name, and the constraint the choice has to satisfy, what may not change and what the project already pins. Never a version, a file's name or extension, a flag, or a guess at what the run will find: those are `/apply`'s to settle by running, inside the constraint, and its record says what it chose. A constraint no run satisfies is the page being wrong, and `/apply` stops and says which, as with a doc the delivery contradicts. ## Entities and invariants

There are four things in this project that have rules about them. None of
them is a row in a database; all four are sets of files, and the invariants
are the sentences a reviewer can check by looking.

### The kit

What it is: this repository. Source of everything installed elsewhere.

Invariants:

* `VERSION` is bumped by any change a target repository would want. A
  change to a skill, a manual, a template or the CLI's behaviour is such a
  change; a change to this repository's own `docs/` is not.
* Every file is either kit-owned, project-owned, merged or appended once.
  There is no fifth category, and a new file declares which it is in the
  delivery that adds it.
* The commands are stack-agnostic. A command that names a language, a
  framework, a test runner or a deploy target has leaked a slot; the slot
  belongs in the target's `docs/05-Process.md`.
* Nothing the kit writes contains an em dash.

Transitions: a version ships when a person commits. There is no release
artifact, no tag flow, no package registry. A target gets the new version by
running `focus-kit update`.

What it is not: a library, a framework, or a runtime dependency of the
target. After `install`, nothing the target itself holds imports or calls
the kit: no code of its own, no build step, no hook. What does call it is a
Command, at every close of `/initialize`, a first run and a review alike,
which runs `focus-kit doctor` in the target and prints what it says. Apart
from that close, `bin/focus-kit` is needed again only to update.

### The target repository

What it is: any git repository the kit is installed into, including this one.

Invariants:

* After `install`, `doctor` reports every kit-owned path present, no
  drift, and the installed version equal to `VERSION`.
* `install` is idempotent. Running it twice leaves the same tree: the trees
  are overwritten, the JSON merge is by key, the two fragments are guarded by
  their markers.
* `install` never removes anything from a target's `.claude/settings.json`,
  with no exception since `mcp-leaves-the-baseline`. It never edits a
  project-owned file. What an earlier kit merged and this one no longer ships
  therefore stays, and `doctor` names it as a Leftover.
* A target whose `docs/00-Product.md` exists is a repository `/initialize`
  reviews, not one it rewrites.

Transitions: absent, installed, initialized, stale (installed version below
`VERSION`), updated.

What it is not: a fork or a clone of the kit. A target holds copies of the
kit-owned files, the installed version and the manifest, and nothing else
of the kit's.

### A delivery

What it is: one page in `work/<slug>.md`, and the work it names.

Invariants:

* It fits on one page. If it does not, it is two deliveries. The page is the
  test that the scope was understood.
* Its **Contract** section is exact. It is the only section that is
  expensive to reverse, so it is the only one precision is demanded of.
* It is defined before it is built, in a separate session. Deciding and
  doing are separated on purpose.
* Its "Done when" is mechanical: every line is something a person can check
  without judgement.
* A delivery that changes behaviour updates the document that owns that
  behaviour, in the same delivery.

Transitions: `[ ]` in the queue, `[>]` once `/propose` wrote the page, `[x]`
once `/apply` finished and moved the page to `work/done/`.

What it is not: a task, a ticket, or a unit of time. It carries no estimate
and no assignee.

### The queue

What it is: `docs/06-Queue.md`, the ordered list of deliveries.

Invariants:

* One line per delivery. The order they will be done in starts at the first
  milestone; the lines under "Later, not scheduled" are wanted and not
  ordered, so a `[ ]` line there is not the next one.
* Every milestone carries a paragraph saying what closes it, and a line is
  placed against that paragraph and not by taste: the milestone whose
  paragraph admits it, the milestone whose paragraph the person amends to
  admit it, or Later.
* A line never leaves. It changes mark. A cancelled delivery is struck
  through with a reason, not deleted, because the reason is the value, and
  so is a Later line another delivery already did.
* The order is the decision. A line moved up is a decision someone took, and
  it is taken in conversation, not by an agent rearranging the file. The two
  moves `/discuss` makes, promoting a Later line and carrying three of them
  into a milestone the person accepted, are that conversation and not an
  exception to it.
* Every finding confirmed by a milestone review becomes a line, named after
  what it fixes.

What it is not: a schedule, a narrative, or a backlog of ideas. Deliveries
that are wanted but not ordered live under "Later, not scheduled", as `[ ]`
lines in the queue's own shape and never as prose bullets, and they leave
that block only through `/discuss`.

## Language of the interface

The kit has no graphical interface. The text a user reads is the terminal
output of `bin/focus-kit` and the three manuals it installs, plus whatever
the commands say in a session.

Every string the CLI prints is in English, including in a target repository
whose documentation language is something else: the terminal output is not
translated, and neither are the skills or the templates.

The three manuals are the exception, and the only one. Since
`manuals-follow-the-language` a target whose documentation language is not
English reads them in that language, because they are documents of that
repository and a manual nobody reads teaches nothing. What translates them is
`/initialize`, never the CLI, which has no model: the kit ships one English
manual, `install` and `update` write it over whatever is there, and the
command run again puts the translation back (`docs/adr/ADR-0008`). Every
section heading stays in English whatever the language, since a Command names
the section it reads and `doctor` matches a Manual citation against the manual
at `KIT_DIR`.

The no em dash rule applies to every line of that output, and to a Translated
manual like to every other text the kit's commands write.

The terminal output has four shapes and no others (`bin/focus-kit:56`):
`say` for plain lines, `ok` for a green check, `warn` for a yellow warning
that does not stop the run, `die` for a red error that exits. A new message
picks one of the four.
